## Abstract

Evaluating changes to interactive reasoning agents is difficult when each run is costly and outcomes depend on stochastic, long-horizon trajectories. We study this problem on an open ARC-AGI-3 agent built on the Duck harness and Qwen3.8-Flash-Next, a stack that ran mid-pack on the public leaderboard. In three frozen ten-game sessions, control arms of one identical configuration differed by 3.33, 3.20 and 1.23 points depending on the session, and four submissions of one code version produced public scores ranging from 24.38 to 29.60. These observations show why isolated score differences can mislead harness decisions, while the available repetitions are too few to define a general detection threshold. Request-level logs from two 25-game calibration runs add a second measurement issue: 15.0% of analyzer requests hit a 120-second client timeout, and the timeout-terminated requests account for 37.5% of cumulative request duration. Extending the timeout changed the error profile without producing a demonstrated score improvement. We describe a repeat-controlled evaluation protocol for this setting, show with a retrospective audit that its decision rules change how many of our own candidate changes would have been kept, and report harness modifications whose local gains were not resolved by leaderboard evidence. The run artifacts and analysis scripts are packaged for release under MIT-0.

## 1 Introduction

ARC-AGI-3 is an interactive reasoning benchmark: video-game-like environments where an agent must perceive a board, act on it, and infer the rules while playing. No instructions are given, and the competition form adds hard operational constraints. Submissions run as Kaggle notebooks on a single RTX PRO 6000 with no internet access, for at most nine hours, and prize eligibility requires open-sourcing the method. Whatever intelligence the agent has must fit on one GPU.

This paper is about a smaller question than solving ARC-AGI-3. It is about how you decide whether a change to an agent stack helped. We entered the back half of the competition with a working stack of the kind many teams ran: Tufa Labs' Duck harness, a tool-using solver in which the model writes Python to inspect the board and act, carried forward by Daniel Franzen's milestone-2 solution and served with Qwen3.8-Flash-Next under SGLang. Our public score sat near 30. We had a list of candidate improvements, a small GPU budget, and for several days we made the mistake this paper is about: we believed single comparisons, because a run costs hours and a rerun feels wasteful.

Two observations forced a change of method. A drift control that we added almost as an afterthought, a repeat of the baseline configuration run at the end of the same session, came back 3.33 points above its twin. And the leaderboard itself scored our byte-identical code at 29.28, 24.38, 29.41 and 29.60 across four submissions. Once those facts sit next to each other, most of the tuning advice in the competition threads becomes unreadable, including our own.

The paper has one method and two case studies. The method is a repeat-controlled evaluation protocol for experiments under a constrained compute budget: frozen game sets, same-session control arms bracketing every comparison, decision rules that report insufficient evidence instead of small wins, and a rule that every number must be recomputable from stored artifacts. The case studies apply it to the two questions we could afford: how large the same-configuration variation is on this benchmark (Section 4), and where the compute budget actually goes (Section 5). Section 6 reports what we tested against the protocol, what the leaderboard could resolve, and what remains unknown.

We did not find a large score improvement, and our entry is mid-pack. The dataset behind the strongest inference in this paper is four leaderboard reruns of one build, three sessions of same-configuration controls, and four screens of a frozen ten-game set. Those are small samples, and Section 8 says so again. What we can offer is a protocol that anyone with the same hardware can run in a few hours, a set of negative results that competition write-ups usually omit, and an account of the compute budget that helps explain why some changes did not show reliable gains in our experiments. The code, the harness patch, the run logs and the analysis scripts will be released before the paper deadline.

## 2 Related work

**Reproducibility and statistical reporting.** The practice of comparing point estimates from a handful of runs is old, and the recommendation against it is old too. Henderson et al. showed in 2018 that variance in deep reinforcement learning can swamp algorithm differences, and argued for repeated runs and reporting discipline.[5] Agarwal et al. pushed the same argument into methodology: interval estimates instead of point estimates, performance profiles for qualitative comparison, robust aggregates such as the interquartile mean, and a public library to compute them.[6] Our setting differs in ways that matter for the protocol. Their runs are independent, seeded training runs on a suite of tasks; our runs share one GPU and one inference server, game outcomes are long-horizon trajectories whose seeds cannot be fixed, and the scoring environment that matters most (the competition rerun) cannot be repeated on demand. Sections 3 and 4 describe how the protocol adapts their recommendations to that setting. We claim no novelty for the idea of repeating experiments; the contribution is the concrete evaluation protocol and the resource accounting, validated on this benchmark.

**What wins here.** The papers that took this competition's paper awards in 2024 and 2025 introduced new learning or search mechanisms: induction plus transduction,[16] test-time training,[17] latent program search,[18] tiny recursive networks,[13] evolutionary program synthesis,[14] and compression-driven learning without pretraining.[15] Each reports substantial score gains on a small number of runs. How much of such a gain survives a repeat is a question the wider community has only recently begun to ask, and 2026 work on agent reproducibility has taken it up directly: an intensive replication study of coding agents across 584 runs found run-to-run variation exceeding the differences between agent-model pairings,[19] and a reproducibility standard for agent research makes rollout records, not reported scores, the unit of publication.[20] Our contribution is not the observation that reruns vary; it is a concrete evaluation protocol and request-level resource accounting for this competition's particular constraints, demonstrated on our own entry.

**ARC Prize and its tracks.** ARC Prize 2026 runs three tracks: a static reasoning benchmark (ARC-AGI-2), the interactive benchmark we compete on (ARC-AGI-3), and a paper prize for work that advances the understanding of how to reach strong ARC performance.[1] The paper track requires a write-up linked to a Kaggle submission, with the submission's score feeding one of six equally weighted rubric categories; the submission need not score highly.[1][2] Our entry links a mid-pack submission at 30.21 and the analyses below.

**Scoring.** ARC-AGI-3 scores relative human action efficiency (RHAE). For each completed level, the agent earns the square of the ratio of human baseline actions to agent actions, capped at 1.15, and the level scores are averaged with the level index as weight; the game score is additionally capped at the weighted fraction of levels completed, and the benchmark score is the mean over games.[3][4] Section 7 reads our results through that formula rather than through informal accounts of difficulty.

**The stack we build on.** The Duck harness from Tufa Labs won the first ARC-AGI-3 milestone.[9] Its design, carried into the milestone-2 solutions, is a tool-using solver: the language model reasons in text, writes Python in a sandbox to inspect the board and probe mechanics, and executes game actions through the same interface. Franzen's milestone-2 solution is the base of our entry, and his write-up documents the changes he found most impactful: a larger context window, exposing animations and difference images, making UNDO available, and a scheduler that spends more compute on games showing promise. He also reports what did not work, including repeated-state guards and a death ledger, which matches what we found.[7]

**Memory and exploration.** Two recent papers frame the problem differently from configuration tuning. PRO-LONG keeps a structured interaction log and lets the agent search it programmatically, reporting an average gain of 18.0 percentage points over a base coding agent on the ARC-AGI-3 public set with frontier models.[10] A 2026 study of the public set finds that every one of the 25 public games can be reached by non-intelligent strategies, so public-set scores cannot discriminate intelligent exploration; the private evaluation is the real test.[11] Both results shaped how we read our own numbers: the public set is a weak proxy, and the lever with the strongest published evidence is memory, not prompt engineering.

**Variance reports in this competition.** Variance is not a private discovery. Lohit's milestone-2 write-up reports the same notebook submitted three times scoring 5.02, 5.50 and 6.42, and a practice run of 37 turning into 9.98 on the leaderboard.[8] He describes the response we arrived at independently: compare runs at equal generated tokens rather than equal wall time, prefer full-length runs, and read transcripts instead of trusting scores. What the public record lacks, and what this paper tries to supply, is a stated protocol with decision rules rather than a warning.

## 3 Setup

**Hardware and stack.** One NVIDIA RTX PRO 6000 (97,887 MiB reported). Qwen3.8-Flash-Next in Intel's W4A16 AutoRound quantization, with a separate INT4 MTP draft model for speculative decoding, served by SGLang Pennyroyal v2.5.3 on the pinned Python 3.12 image, offline. The harness runs with a 131,072-token window, a 12,288-token output cap, KV cache in FP8 E4M3, context evictions that drain roughly 58 Ki tokens at a time (`ARC3_CONTEXT_DRAIN_TOKENS`, a token count and not a byte size), and admission limited to ten concurrent game streams. These values match Franzen's open milestone-2 configuration; we verified them against his write-up and against the source of the submitted notebook (`docs/rerun-config-audit.md` in the open-source tree).

**Our patch.** On top of the published source bundle we apply our own harness patch, 16 files and roughly 7,136 added lines, which adds 94 environment switches. All switches default to off unless a run turns them on; a run's effective configuration is the switch set it enables, and only that set appears in the tables. The switches cover history trimming, prompt variants, vision helpers, persistent Python functions, scheduling, and the guards discussed in Section 6. Applying the patch to the published bundle is verified mechanically; the patch hash and the bundle hash are recorded with the release. The statements in this paper about third-party code are limited to what we changed; attribution and licenses for inherited material are listed in `THIRD_PARTY_NOTICES` in the release, and our MIT-0 license covers only our own additions.

**Batch runner.** Experiments run under a small supervisor that gives each arm its own worker process, writes native artifacts only, never imputes a score for a failed game, and stops the batch when a safety bound trips. An arm is a `(profile, budget, environment overrides)` tuple; because the overlay is applied per worker, one run can compare several arms against one server and one game set. A cold server start costs about 25 minutes of the budget, so the server is restarted only when a serving knob changes.

**Game sets and budgets.** Screens use the first ten games of the sorted public list, 2000 seconds per game, one pass, ten streams. Calibration runs use 25 games; the per-game ceiling is 2900 seconds except for a4, which raises it to 7200. Both sets are frozen and shared across the arms of a run. For reference, the competition rerun gives each of 110 games a much larger budget, a 532-minute wall-clock ceiling with the same ten streams.

**The protocol, and when we adopted it.** The bracketing protocol described here was adopted part-way through the project, and this section distinguishes what followed it from what predates it. A fully bracketed screen contains a baseline arm, one or more candidate arms, and, executed last, an identical repeat of the baseline; the arms run in a fixed order against one server, so we call the first and last arms same-session control arms rather than concurrent runs, and we report the gap between them as the observed same-configuration variation of that session, not as a time trend. Two screens (E5b and E6) follow this design in full. The E5 screen predates it and lost its last arm to an infrastructure failure, so its candidate reading has no end control; the 25-game calibration runs (a3, a4, a5) are single-execution runs of a different kind and are used for latency observation and, in one case, a nominally matched comparison. A candidate is read against both the baseline beside it and the end control: if its margin over the end control is smaller than the session's observed variation, the comparison fails the screening heuristic, and we record it as unresolved. The heuristic is a bookkeeping rule for our own decisions, not a statistical test; it was applied retrospectively across this paper's record rather than prespecified for the early sessions, and we do not treat any of its thresholds as transferable to other settings. Batches record per-request timings from the harness's event log and per-game scores from the native metrics, so every mean in this paper can be recomputed from artifacts rather than trusted from a summary line; `tools/build_numbers.py` performs that recomputation.

**Run comparability.** Where two runs are compared for an intervention effect, we state exactly which keys differ. The pair used for the timeout intervention (runs a3 and a5) differs in four settings, which are listed in Table 2; the other three are budget companions of the first one and were changed with it deliberately. The pair used for latency anatomy (a4 and a5) differs in more, including the per-game ceiling and the number of sessions competing for the ten admission slots, and is used for observation only. Appendix A lists the traps we hit while building this out.

We treat the within-session gaps (3.33, 3.20, 1.23) as the observed same-configuration differences of their sessions, not as a statistical noise floor, and the fact that they vary by a factor of almost three under one benchmark and one stack is the point. Three measurements still cannot estimate a distribution, a confidence interval, or a detection threshold; what they can do is falsify the assumption that same-configuration runs agree, which is the assumption most single-run comparisons rest on. The leaderboard spread, four samples of one build, says the same thing at the scale that decides prizes. None of these numbers transfers to a different setting, and none should be quoted as a constant. A second caveat: a difference between two same-configuration arms is not evidence of drift over time. Two runs can differ through sampling, through trajectory divergence, or through environment changes; separating those would need more repeats than we could afford, and the E7 session, whose baselines do not rise monotonically, is a reminder that the first two sessions' end-arm bump need not be a trend.

The E7 session carries a second lesson that reaches further than the baselines. Variance is not symmetric across configurations. In that one session the three baseline arms spread within 1.23 points, sample standard deviation 0.63, while the three guard arms spread 6.23 points, sample standard deviation 3.12, and their three paired differences had a sample standard deviation of 2.50, with a range of 5.00. A team that measures only the baseline's variability would understate how uncertain the candidate's own result is: baseline variability alone can be insufficient for screening an intervention, because the candidate configuration may be substantially more variable than the baseline it is compared with. Whether that asymmetry reflects a trajectory-altering mechanism that helps only in some runs, or sampling and order effects amplified in longer runs, cannot be decided by three pairs. What the data supports is the caution itself.

These are not artifacts of our harness. Lohit's milestone-2 write-up reports the same notebook submitted three times scoring 5.02, 5.50 and 6.42, and a practice score of 37 turning into 9.98 on the leaderboard.[8] In the milestone comparison thread, participants swap single-run before-and-after numbers and hedge them as guesses, which is the epistemic situation this benchmark forces on anyone without a spare GPU week.[12]

Two practices follow, and we adopted both for every number in this paper.

First, a screen needs its own control. Absolute local scores move between sessions by about two points and vary within a session, so a candidate is read only against an arm that ran in the same session, over the same frozen game list, behind the same server.

Second, comparisons need a bracketing control. Our protocol places an identical copy of the baseline at the end of the batch, and a candidate whose margin over the end control is smaller than the session's observed variation is reported as unresolved. In the E5b screen that variation was 3.33 points and in E6 it was 3.20, which is why several results whose margins fall inside that band carry the label "inconclusive" instead of "gain".

A third practice is cheaper: read transcripts, not just means. A screen can lose points because one game collapsed, and only the transcript tells you whether that was a bad idea or a bad roll of the sampling dice. Section 6 uses that reading twice, once for a game the guard solved in all three runs, and once for the same game solved by a control arm in a fourth.

## 5 Where the compute goes

If the observed variation dictates what can be measured, the compute budget dictates what can be tried. The competition rerun gives a run nine hours of wall clock, ten concurrent game streams, and a per-game ceiling of 532 minutes. The question that matters for harness work is not how much compute there is but where it lands.

Each worker writes a request-level event log and the serving process writes a per-request summary line. Merging those gives Table 2, which puts the stock 120-second analyzer timeout next to a doubled one.

The pile-up at the cap is the tell. The 90th percentile in the first run sits at 120.1 seconds, and 225 requests end there. The timeout-terminated requests alone account for about 7.5 hours of request duration, 37.5% of the 19.98-hour total, and they dominate the error difference between these two runs, 235 against 53. Two readings of that share are tempting and both are too strong. Request duration is not GPU time: the server interleaves up to ten streams, and a request that occupies the queue is not a request that occupies the card. And a terminated generation is not automatically a worthless one: part of what a long generation produced may have shaped the agent's next steps, and our logs do not let us separate valuable long reasoning from wasted long reasoning. What the number does establish is that a third of the analyzer's cumulative request budget went to requests the client itself cut off, which makes the timeout a first-order term in resource planning, whatever its score effect.

Its score effect remains unresolved, and the observed direction is a drop: 24.20 against 27.40 for the nominally matched run with the shorter cap. Raising the cap moves the discarded trade into completed ones: at 240 seconds the cap terminates 38 requests instead of 225, and the reported error count in that pair falls from 210 to 53, although the count is itself a multi-key comparison, since the three budget companions changed with the cap and can affect execution paths, truncation behaviour and real work. Because each configuration ran once and the intervention included the companion keys, the comparison can identify neither a stable beneficial nor a stable harmful score effect.

The generated-token distributions explain why the tail is where the work is. Over both runs the median request generates about 1,300 tokens, the 90th percentile generates 4,265 to 5,099, and the largest single generation reaches the 12,288-token ceiling in the second run, where long generations are no longer cut off at 120 seconds. Roughly 22% of requests exceed 3,000 tokens in both runs. We cannot show that the longer generations bought score; we can show that they absorbed most of the tail, and that giving them more room did not change the outcome we can measure.

The guard result deserves the detail, because it is the clearest case of a local estimate that the leaderboard could not resolve, and because the mechanism is sound on inspection. The guards watch the board state outside the border of the play area. When an action leaves that state bit-identical, they record the triple of (level, state, action) and refuse to execute the same action again in the same state. A refused action arms a single slot: if the model immediately re-issues it, it executes, which keeps the guard from sealing off a hypothesis it got wrong.

Across four sessions the guard arm ran six times. Two of those runs belong to fully bracketed screens (E5b, E6) and three to the alternating E7 matrix; the E5 run has no control. Read as first-baseline differences, the six runs beat their control arm by +9.12 (E5), +5.54 (E5b), +8.91 (E6) and +2.72, +5.13, +0.13 (E7 pairs). Five of the six comparisons carry a screening condition, two of the bracketed kind and three of the alternating kind, and the two designs are not interchangeable, so we report them separately: one of two bracketed comparisons and two of three alternating comparisons satisfied their respective exploratory screening conditions. These conditions flag observations for further study, not statistical significance, and the guard runs' own dispersion, far wider than the baselines' in the same session, prevents a reliable estimate of the guard effect. The per-game tally over all sixty comparisons (six guard runs against the designated control arm of their screen; a tie is a difference below 0.01 points) is 22 wins, 15 losses and 23 ties, though those sixty reuse the same ten games and are not independent units. On ft09, guards have reached 100 points in three of their six runs, against two such solves in thirteen non-guard arms across the four sessions; in E7 the game gave a smaller guard gain in one pair (28.57 to 45.27) and ties in the other two, so the clean three-for-three ft09 story of the earlier sessions does not extend. A second game, cd82, improved with the guards in four of the five paired comparisons (largest +44.7). With ten games to a screen, one flipped game moves the mean by up to ten points, which is the trap this protocol exists to catch.

On the leaderboard the guard build was submitted twice and scored 29.89 and 30.21 (mean 30.05) against the build it replaces, whose four samples average 28.17. Both readings are descriptive and unpaired: +1.88 against the older build's mean, +0.61 against its best sample, and the guard build's own two samples differ by 0.32. None of that is an intervention estimate. Franzen reports the same kind of result from the other side of the competition: he explored repeated-state guards, remembered no-op or fatal-action guards, and a death ledger, and left them out of his submission for lack of clear benefit.[7] Two independent attempts, one of them by the milestone winner, found nothing either could confirm.

The rows that needed no new measurement are worth naming for the same reason. The competition's largest published jumps come from retaining information: Lohit switched to an FP8 KV cache and spent the freed memory on history, and the change "took the score from 14.49 to 22.53"; the milestone comparison thread describes the same trade at the same magnitude.[8][12] Our own calibration agrees in direction, since the base configuration we run already spends its memory on a 131k-token window and a 58k drain, and our attempts to go further by adding structure (memory sections, level inventories) did nothing measurable. The difference between what those teams did and what we tried is the mechanism, not the goal: they bought more room for the agent's own history, and we added more instructions about what to put in it.

**Evidence strength.** The rows of this paper rest on different amounts of evidence, and Table 4 states it rather than leaving the reader to sort it out. Nothing in this paper rises to the level of a repeated controlled comparison on the target environment; the leaderboard samples are descriptively useful and statistically weak.

## 7 Why the score responds this way

The scoring rule shapes everything above, and it is worth stating precisely. ARC-AGI-3 scores relative human action efficiency.[3][4] For a level `l` in a game `e`, with the agent taking `a` actions and the human baseline, an upper-median of first-time human players, taking `h`, the level score is the squared ratio `(h / a)^2`, capped at 1.15 so that a single shortcut cannot dominate a game. A game's score is the weighted average of its level scores, with the level number as the weight, so level five counts five times level one, and it is additionally capped at the weighted fraction of levels completed. The benchmark score is the mean over games. Three consequences follow.

Depth dominates, twice over. An unsolved level scores zero and also lowers the game's cap: a game with five levels where four are cleared can score at most 10/15, or 66.7%, however well those four were played. One game that flips from unsolved to completed is therefore worth up to ten points on a ten-game mean, more than any efficiency change can deliver, and the level weighting means the late levels carry the most weight per level. This is why screens of ten games are this noisy, and why the same-configuration variation of Section 4 sits where it does.

Efficiency is penalized quadratically, but in the runs we inspected it is not the binding constraint. On levels our agent does solve, it is already at or below the human action count. One arm's trajectory on ar25 used 17, 17, 43, 30 and 33 actions against human baselines of 32, 50, 75, 37 and 89 for the five levels it cleared, which earns full or capped credit on each. Once the agent understands a level, its actions are few; the cost of not understanding it is bounded only by the budget, since the agent keeps acting without progress until the level's limit stops it, and the square turns a twofold excess into a quarter of the credit.

Compute has diminishing returns in the place where it is easiest to spend. In our runs, longer deliberation per action did not repair a wrong world model: doubling the analyzer request timeout in the Section 5 experiment changed the error profile (210 to 53 in the matched pair) without a score change we could measure. Whether longer deliberation helps in other settings is untested here. Longer context and better memory are a different matter, and they are the interventions with replicated published gains on this benchmark.[8][10] If we were continuing rather than writing up, we would stop re-tuning switches and start building the searchable interaction log that PRO-LONG describes, which a small model on one GPU needs even more than a frontier one.

The last piece is why local screens are weak proxies for the leaderboard, beyond variance. The study of the public set cited above shows that the entire game set is reachable with non-intelligent strategies, and that the private evaluation is the only real test.[11] Lohit watched a 37-point practice run turn into 9.98.[8] Our two best builds sit within 0.6 points of each other on the leaderboard, 29.60 and 30.21, while their local readings differ by more than five points. Local measurement is useful for finding regressions and for tearing down broken mechanisms, and this paper shows it can be made disciplined enough to do that; it is not a ranking device, and treating it as one is the specific failure mode this paper documents.

## 8 Limitations

We report from one machine, one model, and one competition entry, and several reviewer questions have no good answer in the current data.

The samples are small in the way that matters. Same-configuration variation rests on three sessions of control arms (two, two and three samples) and four leaderboard samples of one build; none of that estimates a distribution, and no number in this paper should be read as a detection threshold. The guard's leaderboard evidence is two submissions of one build against four of another, unpaired, which bounds the effect only above roughly five points; a real effect of one or two points cannot be excluded by anything we ran. Four screens of ten games each are enough to catch a game-sized flip and not enough to estimate an effect size, which is why the guard row reads inconclusive and not "no effect" or "works".

The comparisons are not all clean. The a3 and a5 runs differ in four settings, all named in Table 2, of which one is the intervention and three are its budget companions; that is close to a single-factor comparison and not identical to one. The a4 and a5 runs differ in more than the timeout and are used only for observation. Where we report a local estimate against a same-session control, the arm order is fixed by the batch, so an order effect and an intervention effect cannot be separated without a reversed-order replication, which we did not run: in the E7 matrix, each candidate arm always follows the arm it is compared with.

Selection is a real risk in a paper about measurement discipline. We ran many small screens over the competition, several aborted by infrastructure failures, and the tables here report the runs that completed with usable artifacts. Appendix C lists every experiment we started, its state, and why it entered or left the analysis. Decisions about what to report were made after seeing the artifacts; we have tried to make that safe by reporting estimates against controls and by keeping negative and inconclusive rows in the table rather than dropping them.

Finally, local measurement inherits the public-versus-private gap. The public set is reachable by non-intelligent strategies,[11] the private evaluation is the only test that counts for the prize, and no local number in this paper can be read as a leaderboard prediction. What the protocol can do is keep a team from shipping noise and from abandoning a mechanism for the wrong reason.

## 9 Conclusion

The practical content of this paper is a protocol and a table. The protocol: keep the game set frozen, bracket every batch with an identical control arm, report the gap between controls as the session's observed variation, read candidates against the control rather than against the previous session, and let estimates that do not clear that variation carry the label that says so. The table: of the changes we could test, none is resolved by leaderboard evidence, and the two interventions with published, replicated gains on this benchmark, both of which buy the agent more room for its own history, are the two we could not fully implement here.

For anyone entering the next round of this competition, the advice is unglamorous. Spend your first GPU day measuring your own variation, because the number you find will change what you believe about every change you are about to make. Then spend your effort on what the agent remembers, not on how cleverly it is told to behave. The rest, as one participant put it while comparing the milestone winners' approaches, is inference engineering.[12]

## Appendix A. The screen protocol, and the traps

**Artifact layout.** One run directory per batch contains a `serve.log`, one worker directory per arm with `metrics.json`, `score.json`, `request-events.jsonl` and the transcripts, and a `batch-status.json` recording the state of every arm. A batch that trips its safety bound stops with partial artifacts; those arms are labeled incomplete and excluded from means rather than patched with imputed values. Every table in this paper is regenerated by `tools/build_numbers.py`, which cites the artifact path per number.

**Budget arithmetic.** A six-arm screen costs `setup + 6 x (game budget + worker overhead) + teardown`. With the 5400-second setup ceiling, 2000 seconds per game and a 260-second overhead, the ceiling arithmetic is 5400 + 6 x 2260 = 18,960 seconds, or 5 hours 16 minutes, before teardown; with the typical 25-minute model load the same screen lands near 3 hours 50 minutes. The alternating repeat matrix (E7) uses the same arithmetic: six arms, three of them identical baselines, alternating A-B-A-B-A-B. Each candidate sits directly after the arm it is compared with, which controls position; the design does not close the bracket on a final baseline, so we read it as three paired deltas plus three same-configuration samples rather than as a fully bracketed screen. The batch stops early when its own deadline nears, which is why aborted screens have partial arms rather than a corrupted total.

**Six traps we hit, and the fix.**

1. A model load under storage contention can take 75 minutes instead of 10. Fix: a 5400-second setup ceiling and a readiness probe that checks the server answers one request before any arm starts.
2. A shared-cache flush probe with a 15-second budget aborts the whole batch when the cache host is slow. Fix: a bounded retry on the probe, and a batch status file that records the failure reason instead of killing the run.
3. Notebook cells serialized without their trailing newlines turn a whole cell into a single comment line. Fix: a serializer that preserves line endings, plus a `compile()` check on every generated notebook before it is pushed.
4. Arm definitions that are not all the same tuple shape fail at `ARMS[arm][2]` deep inside the batch. Fix: a self-check that asserts every arm is a `(passes, budget, overrides)` triple before any push.
5. Status watchers that match substrings can read a network error text as a terminal state. Fix: match exact status tokens only, and treat everything else as still running.
6. Kaggle file downloads fail from this host over one path and succeed over another: the list API answers only on a direct connection, the file host only through the local proxy. Fix: two-phase fetching with opposite network settings, and a retry ladder on both phases.

**Decision rules.** A candidate wins only if its margin over the end control exceeds the session's observed variation; the rule was applied retrospectively to the screens that predate the protocol and used prospectively after it. After the screen, the label is chosen from the four in Table 3 and cannot be upgraded without new samples. Estimates are recomputed from artifacts before any claim leaves the analysis, and negative rows stay in the tables.
